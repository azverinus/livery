# iOS guide

This guide makes config values from `livery.yaml` reach an iOS app's build: its build settings, such as the bundle identifier and the signing team, and its Info.plist, such as the display name.

livery writes one xcconfig file. Xcode reads it as a set of build settings, and the project refers to them as `$(KEY)`. livery never edits the Xcode project; the wiring below is done once, by hand.

## 1. Generate an xcconfig

Give the iOS values their own section, and add an `xcconfig` output that writes it next to Flutter's own xcconfig files:

```yaml
# livery.yaml
version: 1

defines:
  ENV:
    values: [dev, staging, production]
    default: dev

config:
  common:
    APP_DISPLAY_NAME: Demo
  ios:
    APP_BUNDLE_ID: com.example.demo
    APP_TEAM_ID: ABCDE12345

overrides:
  - when: {ENV: [dev, staging]}
    set:
      common: {APP_DISPLAY_NAME: Demo Dev}
      ios: {APP_BUNDLE_ID: com.example.demo.dev}

outputs:
  ios:
    format: xcconfig
    merge: [common, ios]
    files: ios/Flutter/livery.xcconfig
```

`dart run livery` writes `ios/Flutter/livery.xcconfig`:

```text
// GENERATED BY livery. Do not edit by hand.
// Regenerate with `dart run livery`.

APP_DISPLAY_NAME=Demo Dev
APP_BUNDLE_ID=com.example.demo.dev
APP_TEAM_ID=ABCDE12345
```

Pick key names that Xcode does not use itself, such as an `APP_` prefix. A key named like one of Xcode's own settings competes with that setting: it changes it wherever the target does not set it, and is ignored wherever the target does. A key of your own does exactly what the project refers to it for, and nothing else.

Keys must be valid build setting names, and livery fails on any other key. The [schema reference](schema.md#xcconfig) lists how keys and values are written.

## 2. Include it after `Generated.xcconfig`

A Flutter app's Runner target takes its build settings from `ios/Flutter/Debug.xcconfig` in the Debug configuration and from `ios/Flutter/Release.xcconfig` in the Release and Profile configurations. Each includes `Generated.xcconfig`, which `flutter` writes.

Add the livery file at the end of both:

```text
// ios/Flutter/Debug.xcconfig
#include? "Pods/Target Support Files/Pods-Runner/Pods-Runner.debug.xcconfig"
#include "Generated.xcconfig"
#include "livery.xcconfig"
```

```text
// ios/Flutter/Release.xcconfig
#include? "Pods/Target Support Files/Pods-Runner/Pods-Runner.release.xcconfig"
#include "Generated.xcconfig"
#include "livery.xcconfig"
```

The `Pods` line is there only in projects that use CocoaPods; leave it as it is. If your project has more configurations, such as a `Profile.xcconfig` or one file per flavor, add the same line to each of them, so every Debug, Profile and Release build sees the values.

Keep the livery line after `Generated.xcconfig`. When a file sets a key twice, Xcode uses the last value, so the order decides which file wins a shared key.

Use `#include`, not `#include?`. Both read the file, but only `#include` makes Xcode warn when it is missing, which is what you want to notice after a fresh clone that has not run livery yet.

## 3. Refer to the values from the Xcode project

Xcode ranks build settings, and a value set on the target itself, in the project file, wins over the target's xcconfig. Flutter's template sets several values on the Runner target, `PRODUCT_BUNDLE_IDENTIFIER` among them, so a key you add to the xcconfig does nothing until the target refers to it.

For each build setting livery should own, replace the target's value with a reference to your key:

1. Open `ios/Runner.xcworkspace` in Xcode and select the **Runner** target, then the **Build Settings** tab, **All** and **Levels**.
2. Find the setting, such as **Product Bundle Identifier**. A value in bold in the **Runner** column is set on the target.
3. Set it to `$(APP_BUNDLE_ID)` for every configuration: Debug, Profile and Release.

| Build setting | Value |
| --- | --- |
| `PRODUCT_BUNDLE_IDENTIFIER` | `$(APP_BUNDLE_ID)` |
| `DEVELOPMENT_TEAM` | `$(APP_TEAM_ID)` |

The same edit in `ios/Runner.xcodeproj/project.pbxproj` changes the line in each of the Runner target's three `XCBuildConfiguration` blocks:

```text
PRODUCT_BUNDLE_IDENTIFIER = "$(APP_BUNDLE_ID)";
```

Leave the **RunnerTests** target alone. It does not include Flutter's xcconfig files, so `$(APP_BUNDLE_ID)` would be empty there.

## 4. Refer to the values from Info.plist

Xcode replaces `$(KEY)` in `ios/Runner/Info.plist` with the build setting when it builds the app:

```xml
<key>CFBundleDisplayName</key>
<string>$(APP_DISPLAY_NAME)</string>
```

This works in nested values too, such as the URL schemes under `CFBundleURLTypes`, and in the entitlements file.

A key that is not defined becomes an empty string, without a warning. If a value is empty in the built app, check the spelling of the key on both sides and that the xcconfig is included.

## 5. Regenerate before every build

Neither `flutter` nor Xcode runs livery. Run it before each build that should see new values, with the same defines you pass to Flutter:

```sh
dart run livery -D ENV=production
flutter build ipa --dart-define=ENV=production
```

To pass the defines only once, let `flutter` write them first and have livery read them back from `Generated.xcconfig`:

```yaml
# livery.yaml
dart_defines_file: ios/Flutter/Generated.xcconfig
```

```sh
flutter build ios --config-only --dart-define=ENV=production
dart run livery
flutter build ipa --dart-define=ENV=production
```

A build started from Xcode uses whatever livery last wrote, so run livery before switching environments in Xcode.

livery leaves a file whose content has not changed untouched, not even its modification time, so running it before every build costs nothing when the values stay the same.

## 6. Xcode's xcconfig caching

An open Xcode window can keep values it read from an xcconfig before livery rewrote the file. If a build started from Xcode still shows old values after regenerating, clean the build folder with **Product > Clean Build Folder** (Shift-Command-K) and build again.

## 7. Gitignore the generated file

The generated xcconfig holds the values of one environment, so it changes whenever you build for another one. Do not commit it:

```gitignore
# .gitignore
ios/Flutter/livery.xcconfig
```

`Debug.xcconfig` and `Release.xcconfig` stay committed, with their `#include` lines.

After a fresh clone, run livery once before opening the project in Xcode or building it. Until then the include points at a missing file, Xcode warns about it, and every `$(KEY)` from livery is empty.
