# Android guide

This guide makes config values from `livery.yaml` reach an Android app's Gradle build: its application id, its version code, its build types, and through them the manifest, `BuildConfig` and resources.

livery writes one Kotlin object, and `android/app/build.gradle.kts` reads it like any other Kotlin code:

```kotlin
applicationId = LiveryConfig.APP_ID
versionCode = LiveryConfig.VERSION_CODE
```

The values are typed, `Int` and `Boolean` included, so nothing is parsed in the build script. livery never edits Gradle files; the wiring below is done once, by hand.

This guide covers the Kotlin DSL only: the `.gradle.kts` build scripts that `flutter create` writes.

## 1. Generate a Kotlin object

Give the Android values their own section, and add a `kotlin` output that writes into `android/livery/src/main/kotlin/`, the source directory of the small build that section 2 sets up:

```yaml
# livery.yaml
version: 1

defines:
  ENV:
    values: [dev, staging, production]
    default: dev

config:
  common:
    app_name: Demo
  android:
    app_id: com.example.demo
    app_id_suffix: .dev
    version_code: 42
    minify: false

overrides:
  - when: {ENV: production}
    set:
      android:
        app_id_suffix: ""
        minify: true

outputs:
  android:
    format: kotlin
    merge: [common, android]
    files: android/livery/src/main/kotlin/LiveryConfig.kt
```

`dart run livery` writes `android/livery/src/main/kotlin/LiveryConfig.kt`:

```kotlin
// GENERATED BY livery. Do not edit by hand.
// Regenerate with `dart run livery`.

object LiveryConfig {
    enum class Env { DEV, STAGING, PRODUCTION }

    val ENV: Env = Env.DEV

    const val APP_NAME: String = "Demo"
    const val APP_ID: String = "com.example.demo"
    const val APP_ID_SUFFIX: String = ".dev"
    const val VERSION_CODE: Int = 42
    const val MINIFY: Boolean = false
}
```

The object is named after the file, and its names follow `BuildConfig`: config keys and defines in UPPER_SNAKE, and an enum class per define with `values`. A define without a `default` that is not `required` is nullable, such as `val FLAVOR: Flavor?`, and holds `null` when no source gives it a value. The [schema reference](schema.md#kotlin) lists the naming rules.

## 2. Add the livery build, once

Gradle compiles build scripts before it builds the app, so the object has to be compiled in a build of its own, which the app's build then uses. That build is three small files you add once and never change, whatever livery version you use.

`android/livery/build.gradle.kts`:

```kotlin
plugins {
    `kotlin-dsl`
}

repositories {
    mavenCentral()
}
```

`android/livery/src/main/kotlin/livery.gradle.kts`, an empty file. It defines a plugin with the id `livery` that does nothing; applying it is what puts `LiveryConfig` on the app build script's classpath.

In `android/settings.gradle.kts`, include the build inside `pluginManagement`, next to Flutter's own:

```kotlin
pluginManagement {
    // ...
    includeBuild("$flutterSdkPath/packages/flutter_tools/gradle")
    includeBuild("livery")
    // ...
}
```

In `android/app/build.gradle.kts`, apply the plugin:

```kotlin
plugins {
    id("com.android.application")
    id("dev.flutter.flutter-gradle-plugin")
    id("livery")
}
```

`LiveryConfig` is now visible everywhere in `android/app/build.gradle.kts`, with no import.

The livery build compiles with the Kotlin that Gradle itself ships, not the Kotlin Gradle plugin version your app declares, so it adds no version to keep in step and prints no warnings. When a value changes, Gradle recompiles only the object and the app's build script, which takes a second or two.

The first build after adding it needs network access: Gradle downloads the `kotlin-dsl` plugin from the Gradle Plugin Portal and the Kotlin standard library from Maven Central. Later builds use Gradle's cache.

## 3. Use the values in the build script

```kotlin
// android/app/build.gradle.kts
android {
    defaultConfig {
        applicationId = LiveryConfig.APP_ID
        applicationIdSuffix = LiveryConfig.APP_ID_SUFFIX.ifEmpty { null }
        versionCode = LiveryConfig.VERSION_CODE
        versionName = flutter.versionName
        // ...
    }

    buildTypes {
        release {
            isMinifyEnabled = LiveryConfig.MINIFY
            isShrinkResources = LiveryConfig.MINIFY
            // ...
        }
    }
}
```

- `applicationIdSuffix` is `null` when there is no suffix. A config value is a non-null `String`, so turn an empty suffix into `null` with `.ifEmpty { null }`: the build script then says "no suffix" the way AGP does, instead of relying on how AGP treats an empty one.
- `versionCode` takes the `Int` as it is. Keep `version_code` an integer in YAML, `42` rather than `"42"`, or the build script will not compile.
- Defines with `values` are enum constants, so a branch on one is checked by the compiler:

  ```kotlin
  if (LiveryConfig.ENV == LiveryConfig.Env.PRODUCTION) {
      // ...
  }
  ```

## 4. Pass values to the manifest and the app code

The object exists only while Gradle configures the build; the app never sees it. Hand the values the app needs to AGP, which puts them in the manifest, `BuildConfig` or resources.

### The manifest, with `manifestPlaceholders`

```kotlin
// android/app/build.gradle.kts
android {
    defaultConfig {
        manifestPlaceholders["appLabel"] = LiveryConfig.APP_NAME
    }
}
```

```xml
<!-- android/app/src/main/AndroidManifest.xml -->
<application
    android:label="${appLabel}"
    ...>
```

### `BuildConfig` and resources

The examples below assume an `api: {url: …, timeout: 30}` mapping in the `android` section, which becomes `API_URL` and `API_TIMEOUT`.

`buildConfigField` adds a constant to the generated Java class `BuildConfig`, and `resValue` adds a resource as if it were in `res/values`. AGP 9 generates neither unless you turn them on in `buildFeatures`:

```kotlin
// android/app/build.gradle.kts
android {
    buildFeatures {
        buildConfig = true
        resValues = true
    }

    defaultConfig {
        buildConfigField("String", "API_URL", "\"${LiveryConfig.API_URL}\"")
        buildConfigField("int", "API_TIMEOUT", "${LiveryConfig.API_TIMEOUT}")
        resValue("string", "api_url", LiveryConfig.API_URL)
    }
}
```

`buildConfigField` takes Java source text: a string value needs the quotes around it, as above, and must not hold a `"` or `\` of its own. `resValue` takes the value as it is.

This reaches only the Android side of the app. For Dart code, use a [`dart`](dart.md) output.

## 5. Regenerate before every build

Neither `flutter` nor Gradle runs livery. Run it before each build that should see new values, with the same defines you pass to Flutter:

```sh
dart run livery -D ENV=production
flutter build appbundle --dart-define=ENV=production
```

Once livery has run, builds started from Android Studio or with `./gradlew` in `android/` use the same object as `flutter build`, so they agree on every value. Run livery again before switching environments there.

livery leaves a file whose content has not changed untouched, so running it before every build costs nothing when the values stay the same.

## 6. What the object cannot reach

`android/settings.gradle.kts` cannot use `LiveryConfig`. Gradle evaluates settings before it compiles any included build, the livery one among them. Anything settings decide, such as which plugins and versions the build uses or which modules it includes, stays out of livery's reach.

## 7. Gitignore the generated files

The generated object holds the values of one environment, so it changes whenever you build for another one. Do not commit it, nor what Gradle builds next to it:

```gitignore
# .gitignore
android/livery/src/main/kotlin/LiveryConfig.kt
android/livery/.gradle/
android/livery/.kotlin/
android/livery/build/
```

`android/livery/build.gradle.kts` and the empty `livery.gradle.kts` stay committed.

After a fresh clone, run livery once before opening the project in Android Studio or building it. Until then the app's build script refers to an object that does not exist and fails to compile.
