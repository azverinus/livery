# Dart guide

This guide makes defines and config values from `livery.yaml` reach a Flutter app's Dart code: which environment the app was built for, and values such as an API URL.

livery writes one Dart file per `dart` output. It holds an enum for each define that lists its values, and a holder class with the other defines and the config values. Your code imports the file like any other library.

## 1. Generate a Dart file

Add a `dart` output. A `dart` output merges no section unless it says so, so name the sections whose values the app reads:

```yaml
# livery.yaml
version: 1

defines:
  ENV:
    values: [dev, staging, production]
    default: dev
  BUILD_TAG:

config:
  common:
    app_name: Demo
  dart:
    api:
      url: https://dev.example.com
      timeout: 30

overrides:
  - when: {ENV: production}
    set:
      dart: {api: {url: https://example.com}}

outputs:
  app:
    format: dart
    merge: [common, dart]
    files: lib/src/app_config.g.dart
```

`dart run livery` writes `lib/src/app_config.g.dart`. Shortened, it reads:

```dart
// dart format off
// GENERATED BY livery. Do not edit by hand.
// Regenerate with `dart run livery`.
// ignore_for_file: type=lint

/// `--dart-define=ENV=<dev|staging|production>`
enum EnvDefine {
  dev('dev'),
  staging('staging'),
  production('production');

  final String value;
  static const String rawValue = String.fromEnvironment('ENV', defaultValue: 'dev');
  static const EnvDefine? maybeCurrent = …;
  static EnvDefine get current => …;
  static EnvDefine? tryParse(String? value) { … }
}

abstract final class AppConfig {
  /// `--dart-define=BUILD_TAG=...`
  static const String buildTag = String.fromEnvironment('BUILD_TAG');

  static const String appName = 'Demo';
  static const String apiUrl = 'https://dev.example.com';
  static const int apiTimeout = 30;
}
```

The [schema reference](schema.md#dart) lists how names are formed and the options of the output.

## 2. Read the defines

The defines are not baked in. Each enum reads its define with `String.fromEnvironment`, so it holds the value of the `--dart-define` the app is compiled with:

```sh
flutter run --dart-define=ENV=staging
```

| Member | Type | Value |
| --- | --- | --- |
| `rawValue` | `String` | The define as compiled in, or its declared `default`, or `''` without either. |
| `maybeCurrent` | `EnvDefine?` | The enum value equal to `rawValue`, or `null` when none is. |
| `current` | `EnvDefine` | `maybeCurrent`, or throws a `StateError` naming the define and its values when it is `null`. |
| `tryParse(String?)` | `EnvDefine?` | The enum value equal to the argument, or `null`. |
| `value` | `String` | The value of an enum value, spelled as in the manifest. |

Values are matched exactly, as `String.fromEnvironment` matches define names: `--dart-define=ENV=Production` is not `production`, so `maybeCurrent` is `null` and `current` throws.

```dart
import 'src/app_config.g.dart';

final banner = switch (EnvDefine.current) {
  EnvDefine.dev => 'DEV',
  EnvDefine.staging => 'STAGING',
  EnvDefine.production => null,
};
```

`maybeCurrent` is a constant, so a branch such as `if (EnvDefine.maybeCurrent == EnvDefine.dev)` is decided when the app is compiled, and the compiler drops the code of the other environments from a release build.

A define without `values` has no enum. It becomes a `String` constant on the holder class, read the same way: `AppConfig.buildTag` is `''` when the app is compiled without `--dart-define=BUILD_TAG=…` and the define has no `default`.

## 3. Read the config values

Config values are baked in as constants of the holder class, typed as their value types: `String`, `int`, `double` or `bool`. Nested keys are joined into one lowerCamel name, so `api: {url: …}` becomes `AppConfig.apiUrl`.

```dart
final client = ApiClient(baseUrl: AppConfig.apiUrl, timeout: Duration(seconds: AppConfig.apiTimeout));
```

A config value that is `null` or a list has no Dart constant, and fails generation. Give it a value of one of the four types, or keep it in a section the `dart` output does not merge.

## 4. Commit the defines, gitignore the config

A Dart file has one of two lifecycles, depending on what it holds:

- **Defines only.** An output that merges no section holds only code that reads the defines when the app is compiled. livery writes the same file whatever define values it runs with, so the file changes only when the manifest's defines change. Commit it, and the project analyzes and builds right after a fresh clone.
- **Baked config.** An output that merges sections holds the config values of the environment livery ran for, so it changes whenever you generate for another environment. Do not commit it; generate it before each build.

Keep the two apart with two outputs. Turn `include_defines` off on the config output, so each enum is declared once:

```yaml
outputs:
  defines:
    format: dart
    files: lib/src/defines.g.dart
  config:
    format: dart
    merge: [common, dart]
    include_defines: false
    files: lib/src/config.g.dart
```

The holder classes are named after the files, `Defines` and `Config`; set `class_name` to name them yourself.

```gitignore
# .gitignore
lib/src/config.g.dart
```

After a fresh clone, run livery once before analyzing or building the app. Until then every import of the config file fails.

## 5. Generate and compile with the same defines

A file with baked config holds the values livery chose for the define values it ran with. The enums read the define values the app is compiled with. Nothing checks that the two agree:

```sh
dart run livery -D ENV=dev
flutter build apk --dart-define=ENV=production
```

This app reports `EnvDefine.current` as `production` but talks to `AppConfig.apiUrl` of `dev`.

Run livery before every build, with the same defines you pass to Flutter. One way to pass them once is the `DART_DEFINES` line that `flutter` writes to `ios/Flutter/Generated.xcconfig`, which livery reads with `dart_defines_file`; see [Define sources](schema.md#define-sources). A defines-only file has no such risk, as it holds no values of its own.

## 6. Formatter and analyzer

The generated file passes `dart analyze` with no issues and is left alone by `dart format`, whatever page width your project uses:

- `// ignore_for_file: type=lint` turns off every lint for the file. The code also has no warnings or errors of its own.
- `// dart format off` on its first line tells the formatter to leave the rest of the file as it is, so `dart format --set-exit-if-changed` passes.

The formatter reads `// dart format off` only in a package whose language version is 3.7 or later, which is the lower bound of the SDK constraint in `pubspec.yaml`:

```yaml
# pubspec.yaml
environment:
  sdk: ^3.7.0
```

Flutter 3.29 ships Dart 3.7. With a lower bound below 3.7, the formatter ignores the comment and reformats the file, and a format check fails. Raise the lower bound, or exclude the generated files from the format check.
